02 · Request lifecycle

What happens to POST /v1/models

Every state-changing call follows the same path. Failures short-circuit into one JSON error shape.

1Client callBearer token in the Authorization header, optional Idempotency-Key. The CLI and SDK build this for you.
2MiddlewareOpenTelemetry span (W3C traceparent in, X-Trace-Id out), Prometheus counter and histogram, timing.
3Auth and roleget_principal maps the token to a name and role. require_role("operator","admin") gates the route: 401 or 403.
4Body checksContent type (415), size cap (413), depth and NaN checks, then a strict pydantic model that forbids extra fields: 422.
5IdempotencySame key and same body replays the cached 2xx. Same key, different body: conflict. Still running: 409 with Retry-After.
6Domain callRuns in a thread pool: registry.register(...). A dataset_version is looked up in the DatasetRegistry: unknown means 404. The audit entry is appended here.
7Mirror recordOne lineage node plus an edge to the previous node, a best-effort MLflow mirror when enabled, and a SqlRepo upsert when a real database is configured.
8Response201 with the model record. The result is stored for idempotent replay before it is returned.

All map through install_error_handlers to {"error": {"code", "message"}}. Schema failures are 422 and name fields only; an integrity failure is a bare 500. Domain messages can quote an identifier, e.g. an unknown dataset version.
Green boxes are domain logic; clay boxes are service plumbing. The same numbered path applies to validate, transition, datasets and incidents.
